Infrastructure & Pricing

What it costs to run this, and what to charge for it

A hosting-cost model for the Nigeria LBA Level Traceability app once it moves off a single shared Vercel+Neon deployment onto AWS-backed, multi-tenant infrastructure — and what that implies for per-LBA subscription pricing.

Numbers below are superseded by the Lambda-direct architecture These figures assume App Runner/Fargate compute and an RDS instance. The confirmed direction is now direct Lambda-to-API-Gateway integrations (no FastAPI) against Aurora PostgreSQL Serverless v2, using a new dedicated VPC (no custom VPC existed to reuse) — see infra/resource-mapping/lba-backend-unified-resource-mapping-layer-oriented.json for the current, lower cost model (~$71/mo pilot vs. ~$125/mo below), driven by Lambda's near-zero idle cost and no new NAT Gateway.
Read this before quoting a price Every dollar figure below is a planning estimate assembled from public AWS/Vercel/Neon pricing pages and rate-comparison sites in November 2026, not an invoice. Cloud prices and plan terms change, and real usage always drifts from assumptions. Before you commit to a customer price, re-run the AWS Pricing Calculator and Vercel's own calculator against the provisioning plan's actual instance sizes. Treat this as the thinking, not the quote.

1. What one "LBA" costs to serve

An LBA (Licensed Buying Agent) is one tenant: its own farmer register, its own lot history, its own users. From the real JIMGAF data already in this app, a typical tenant looks like:

  • 500–2,000 registered farmers
  • 3–10 staff accounts (admin / TO / LBA roles), active mostly during business hours
  • Tens to a few hundred lots recorded per month, spiking in harvest season
  • One .xlsx delivery-slip export per lot, one bulk farmer-register upload per season

None of that is heavy by cloud standards — this is a CRUD-and-forms app, not a video pipeline. The cost story here is almost entirely about how many LBAs share the same infrastructure, not about any one LBA's usage.

2. The infrastructure being priced

Per the provisioning plan, "backend on AWS, frontend on Vercel" splits the app into a UI tier (Vercel, serving the pages as today) and a stateful API tier (AWS, holding the database and doing the real work). Four cost centers follow from that split:

  • AWS compute — the FastAPI service that used to be a single Vercel function, now running on AWS App Runner (pilot/growth) or ECS Fargate behind a load balancer (scale).
  • Database — either staying on Neon (usage-based serverless Postgres, zero migration) or moving to Amazon RDS/Aurora for Postgres (flat-rate instances, more control, needed once compliance or private networking matters).
  • Supporting AWS services — S3 for export/backup storage, Secrets Manager, Route 53, CloudWatch, and (once this is paid-for infrastructure with outside traffic) AWS WAF.
  • Vercel — the UI tier's hosting plan, since a paid commercial product needs a Pro (or Enterprise) plan rather than the free Hobby tier.

3. Three points on the growth curve

Infrastructure doesn't scale linearly with tenant count — fixed costs (load balancer, logging, DNS) get shared across more LBAs as the platform grows, so the cost per LBA should fall as you add customers. The three tiers below show that curve.

Why the database is the line to watch Compute and the Vercel bill grow roughly with traffic, which grows roughly with LBA count — predictable. The database is the one line that can jump in steps (micro → small → medium → a read replica) rather than sliding smoothly, because Postgres doesn't scale horizontally the way a stateless API does. Budget for the next instance size up before you need it, and revisit the RDS-vs-Neon decision once a single LBA's reporting queries start competing with another's lot-creation traffic.

4. Database choice: keep Neon, or move to RDS?

The figures above assume a move to Amazon RDS, which is the more "fully AWS" and more predictable option. Staying on Neon (the current provider) is a legitimate alternative, especially early on — it avoids a data migration entirely. Roughly, for the same workload:

Neon (Launch plan)Amazon RDS for PostgreSQL

Pilot-scale monthly≈$40–$70≈$30
Migration effortNone — already in productionOne-time export/import, connection string + pooling changes
Best fitPilot, and anywhere usage is spiky (serverless autosuspend saves money between harvest seasons)Growth/Scale, or once VPC-private networking, IAM-based access, or predictable billing matter more than migration-avoidance

Recommendation: don't migrate the database on day one. Launch the AWS-hosted backend against the existing Neon database (it's already reachable over the internet via its pooled connection string), and revisit RDS once there's a second or third paying LBA and the cost/control trade-off is worth the migration effort.

5. What this means for the subscription price

The per-LBA infrastructure cost falls from roughly $25–125/month at pilot scale down to $12–24/month once the platform carries 50–100 LBAs — classic SaaS economics: fixed costs get shared across more tenants. That curve is useful for margin planning, but it's the wrong thing to price from directly, for two reasons: infrastructure is a small fraction of what it actually costs to run this as a business (support, onboarding, data verification, feature work dwarf the AWS bill), and a price that chases your own falling infra cost down over time gives away margin you should be keeping as the business scales.

A more durable approach is to set subscription tiers by what the LBA gets (register size, user seats, support level) and let margin expand as the shared infrastructure gets more efficient underneath it:

That's a healthy margin even at pilot scale — the risk at pilot scale isn't the infra bill, it's that fixed costs (one RDS instance, one App Runner service, one Vercel Pro seat) are being carried by only 1–5 customers. Don't discount the first LBAs below roughly $100–150/month; that's close to the actual fully-loaded infra cost of the first tenant alone.

6. What this estimate deliberately leaves out

  • Engineering and support time — the actual dominant cost of running a SaaS product at this scale; this document only prices infrastructure.
  • One-time migration work — containerizing the app, standing up the AWS account, and (if chosen) the Vercel/AWS API split described in the provisioning plan — these are development hours, not a recurring bill.
  • Payment processing fees on whatever you charge LBAs (typically 1.5–3.5%).
  • Data transfer and traffic spikes beyond the harvest-season pattern already assumed — a true surge (e.g. a nationwide onboarding push) should be re-estimated separately.
