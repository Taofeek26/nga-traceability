Infrastructure & Pricing

Provisioning the backend on AWS

A phased plan for moving the stateful parts of the app onto AWS while Vercel keeps serving the UI exactly as it does today — plus the one decision that has to be made before any of it starts.

1. The decision this plan depends on

Today the whole app — Jinja2 pages and the Postgres-backed route handlers in app.py — runs as one thing on Vercel. "Backend on AWS, frontend on Vercel as is" only makes sense once that one thing becomes two things that talk over HTTP. There are two honest ways to get there:

Option A — Lift: move the whole app to AWS, retire Vercel's role

Containerize app.py unchanged and run it on AWS end to end. Fastest path, smallest rewrite risk, nothing new to debug across a network boundary. The cost: it doesn't match "frontend on Vercel as is" — Vercel would have no job left to do.

Option B — Split: a real API tier on AWS, Vercel stays the UI

Extract the data-touching logic in app.py (every handler that calls conn.execute(...)) into a standalone FastAPI service deployed on AWS. The Jinja2 route handlers stay on Vercel exactly as they render today, but instead of hitting Postgres directly they make an HTTPS call to the new AWS service. This is what was asked for, and it's the right shape for a real multi-tenant SaaS product — but it's a genuine engineering project, not a hosting change: every route in app.py gets touched.

Recommendation Build toward Option B — it's the correct target architecture for charging multiple LBAs on shared infrastructure, and it's what lets AWS do the thing Vercel structurally can't: hold a long-lived connection pool to Postgres, run exports and bulk uploads without a serverless time limit, and scale the stateful tier independently of UI traffic. This plan is written for Option B. Phase 1 is deliberately scoped as the smallest slice of that split, so the team can validate the approach before committing to extracting every route.

3. Phased rollout

Phase 0

Foundations

~1 week

Set up the AWS account the right way before anything is deployed into it, so Phase 1 isn't undone later:

  • Dedicated AWS account (or an Organizations member account) for this product, separate from any personal AWS usage.
  • IAM: a deployment role with least-privilege permissions, MFA on the root/admin user, no long-lived access keys checked into the repo.
  • A VPC with public and private subnets across two Availability Zones (needed for Multi-AZ RDS and for Fargate tasks later, even if App Runner itself doesn't require one).
  • Route 53 hosted zone for the production domain; ACM certificate request for the AWS-side hostname (e.g. api.<domain>).
Phase 1

Extract and containerize the API service

~2–3 weeks

The actual Option B engineering work. Start with the highest-value slice rather than the whole app at once:

  • Pull the farmer/lot/allocation/export routes out of app.py into a standalone FastAPI service that returns JSON instead of rendering templates.
  • Keep the Vercel app's routes in place, but have them call this new service over HTTPS for data instead of calling database.py directly — start with one route (e.g. lot creation) to prove the pattern before converting the rest.
  • Write a Dockerfile for the new service; build and run it locally against the existing dev Postgres to confirm parity with current behavior.
  • Decide the service-to-service auth: a shared API key in an environment variable is enough to start; move to short-lived signed tokens once there's more than one calling client.
Phase 2

Deploy to AWS compute

~1 week
  • Push the container image to Amazon ECR.
  • Pilot/Growth: deploy on AWS App Runner — it builds from the ECR image, handles TLS, autoscaling, and health checks without a VPC or load balancer to manage.
  • Scale: migrate the same image to ECS on Fargate behind an Application Load Balancer once traffic or cost justifies the extra control (see the cost tiers).
  • Point api.<domain> at the service (App Runner custom domain, or the ALB) using the Phase 0 ACM certificate.
Phase 3

Database

~1 week, or deferred
  • Default: keep the existing Neon database and point the new AWS service at its pooled connection string — no migration, no downtime risk.
  • If/when the RDS trade-off tips in favor of migrating: provision RDS for PostgreSQL Multi-AZ in the Phase 0 VPC's private subnets, pg_dump/pg_restore the data during a maintenance window, cut over the connection string, keep Neon as a cold fallback for a week.
  • Either way: store the connection string in Secrets Manager, not an environment variable checked into any config file.
Phase 4

Observability and backups

~3–4 days
  • CloudWatch log group for the API service; an alarm on 5xx rate and on RDS/Neon connection count.
  • Automated RDS snapshots (or confirm Neon's point-in-time recovery window) with a documented restore drill — run it once before going live, not after the first real incident.
  • Uptime check against api.<domain>/health from outside the VPC.
Phase 5

Security hardening

~3–4 days
  • AWS WAF in front of the ALB/App Runner endpoint once it's carrying paying customers' data — rate limiting and the managed common-threats rule group are enough to start.
  • Confirm every tenant-scoped query still filters by lba_id at the new API boundary, not just in the UI layer — the multi-tenant isolation guarantee has to hold even though requests now cross a network hop.
  • Rotate the service-to-service API key/secret once the pattern is proven, and put that rotation on a schedule.
Phase 6

Cut over and finish the split

ongoing
  • Convert the remaining Vercel routes to call the AWS API, one at a time, in order of how much they matter to an active LBA (farmer uploads and lot creation before read-only reporting pages).
  • Once every route has moved, database.py and the direct Postgres connection can be removed from the Vercel deployment entirely — at that point Vercel genuinely is "frontend only."
  • Re-run the cost estimate against real traffic numbers once the first paying LBA has a full month of usage, and correct the pricing tiers if they're off.

4. What to watch for

  • Latency. Every page that used to do one in-process DB call now does an HTTP round-trip to another provider's network. Measure this in Phase 1 on the first converted route before converting the rest — if it's bad, consider colocating or using HTTP keep-alive/connection reuse before blaming the architecture.
  • Two deploy pipelines. Vercel's own deploy-on-push and a new AWS deploy (ECR push + App Runner/ECS release) now have to ship in a compatible order whenever an API contract changes — version the API responses defensively so a slightly-stale Vercel deploy doesn't break against a newer AWS one.
  • Don't migrate the database just to migrate it. Neon is already in production and already multi-tenant-capable; moving to RDS is a cost/control decision for later, not a prerequisite for standing up the AWS API tier.
