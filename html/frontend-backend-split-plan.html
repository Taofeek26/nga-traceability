Architecture & Migration

Splitting into a React/TypeScript frontend and a framework-free AWS Lambda backend

A plan to carry the current design system and every page over into a proper frontend/ + backend/ split — React/TypeScript on one side, plain Lambda handlers wired directly to API Gateway (no FastAPI, no Mangum) against Aurora PostgreSQL Serverless v2 on the other, using a new, dedicated VPC (an account sweep found nothing to reuse).

This is the plan, not the build Nothing in the live app changes from reading this document. It lays out the decision, the directory layout, the route-by-route mapping, and the risk list, so the actual scaffolding work can start from an agreed design instead of guesswork. Say go and the implementation starts from Phase 1.
This document and the resource-mapping JSON files are the same design, two views The route-by-route table and phases below describe the architecture in prose. infra/resource-mapping/lba-backend-unified-resource-mapping-layer-oriented.json is the canonical, resource-by-resource registry (every Lambda's memory/timeout/env vars/IAM policy, the Aurora cluster's scaling config, the new VPC's CIDR, subnets, and security groups) and -process-oriented.json groups the same resources into business flows. If the two ever disagree, the JSON wins — update it first, then this page.

1. The decision: keep Jinja2 on Lambda, or rebuild the UI in React?

You flagged the real fork yourself: is it still fine to keep the current FastAPI + Jinja2 frontend, or move to TypeScript/React while keeping every component and style exactly as it looks today? Both are real options — here's the honest trade-off.

Option A — Lift the whole app onto Lambda, keep Jinja2

Wrap the existing app.py with the Mangum ASGI adapter and run the entire FastAPI app — routes, Jinja2 rendering, everything — as one Lambda function behind API Gateway, deployed with SAM. Zero template rewrite, zero component rewrite, same macros, same CSS. "Backend on AWS alone" becomes true the moment Vercel is out of the picture. The cost: there's no separate frontend/ directory in any real sense — it's still one monolith, just relocated. This isn't what you described wanting, but it's the fallback if the React rewrite below turns out to be more than the project needs right now.

Option B — True split: React/TypeScript frontend, framework-free Lambda backend (confirmed)

This is what you described, and it's the right target for a product meant to scale to many LBAs: a backend/ SAM app of seven plain Python Lambda handlers — no FastAPI, no Mangum, each one reading event['rawPath'] / event['requestContext']['http']['method'] directly off the API Gateway proxy event — and a frontend/ React/TypeScript single-page app that calls them. The components and styles genuinely do carry over almost unchanged — see §3. The real cost is everywhere a page currently does something only a server-rendered app can do cheaply: sessions, file upload/download, and the one-request-does-everything flow of a POST that redirects to a result page. §5 and §6 cover exactly what that costs.

Confirmed direction Option B, with two corrections to the original draft: the backend runs no web framework at all (seven domain Lambdas behind direct API Gateway integrations, not one Lambda running FastAPI via Mangum), and the database is Aurora PostgreSQL Serverless v2 rather than RDS/Neon, using a new dedicated VPC. The CSS and visual design are still not being redone — only the templating layer (Jinja2 {% %} syntax) becomes React components with the same markup and the same class names. Option A is noted only as a faster escape hatch if the timeline gets tight.

2. What genuinely doesn't change

This is the part worth saying plainly, since "rewrite the frontend" sounds bigger than it is here:

  • Every CSS file carries over verbatim — design-system/css/tokens.css and design-system/css/lba-ui.css (mirrored today at static/ds/) become frontend/src/styles/tokens.css and lba-ui.css, copy-pasted, no edits. CSS doesn't know or care whether the markup above it came from Jinja2 or React.
  • The icon sprite carries over verbatim — templates/partials/icons.html is inlined SVG <symbol> defs; it drops into the React app's root template exactly as it is today.
  • Every class name, every layout, every badge color, every spacing token stays identical — nothing in design-system/docs/foundations.md or components.md needs to change; they describe the CSS, not the templating engine.
  • The business logic barely moves — allocation.py (the proportional-split algorithm) and the quota/eligibility rules in database.py transfer into the new backend essentially unedited; only the thin layer around them (how a request comes in, how a response goes out) changes.

What does change is templates/macros.html (12 Jinja2 macros) becoming 12 small React components, and each of the 10 page templates becoming a React route that fetches JSON instead of a server that renders HTML. That's real but mechanical work — see §4.

3. Target architecture

Where frontend/ is hosted doesn't actually need to change from what you have today — a Vite production build is static files, and Vercel serves static files just as well as it served the old FastAPI functions (or S3 + CloudFront, or AWS Amplify Hosting, work equally well). The only thing being removed from Vercel is the Python runtime; the files it serves become plain HTML/JS/CSS. The full resource-by-resource detail behind this diagram — every Lambda's trigger paths, IAM policy, and VPC config — is in infra/resource-mapping/lba-backend-unified-resource-mapping-layer-oriented.json.

6. Route-by-route plan

The 26 current endpoints in app.py become new paths on the backend, each owned by exactly one of the seven domain Lambdas (full trigger definitions in infra/resource-mapping/lba-backend-unified-resource-mapping-layer-oriented.json) — not a 1:1 rename, since routes that only rendered an empty HTML form (GET /signup, GET /login, GET /upload) disappear from the backend entirely once the React frontend renders those forms itself. No business rule changes — only the response format (JSON, not rendered HTML) and the path/verb shape (REST-ier now that there's no HTML form to submit against).

7. The three things that actually change behavior

7.1 — Sessions: signed cookie → JWT bearer token, verified by a dedicated authorizer Lambda

auth.py today signs a cookie (itsdangerous, carrying user_id/lba_id/org_name/user_name/role) that works because the browser and the app share one origin. Once the frontend and backend are on different domains (app.yourdomain.com vs. api.yourdomain.com), a cookie-based session needs SameSite=None; Secure and gets flaky across browsers/privacy modes. The fix: AuthService issues the exact same signed payload, but as a JWT returned in the login response body — stored in memory on the frontend, sent as Authorization: Bearer on every request. Every protected route then runs through LBA-Prod-Security-JwtAuthorizer, a small custom Lambda authorizer (not API Gateway's native JWT authorizer, since these tokens are self-issued rather than coming from an OIDC provider with a JWKS endpoint like Cognito). It verifies the signature against the key in LBA-Prod-Security-JwtSigningKey and passes lba_id/role/user_id to the domain Lambda as request context — the same tenant-isolation guarantee app.py enforces today, just checked once at the API boundary instead of in-process.

7.2 — File upload/download through API Gateway

The HTTP API has a 10MB payload limit (plenty for the current ~140KB master-data files) and each Lambda has its own timeout (30s for the two that touch files — see the registry). Uploads (small xlsx files) are fine going straight through. Downloads (the template file, the farmer export, the lot delivery-slip export) are served a different way: the owning Lambda writes the generated file to one of the three S3 buckets and returns a short-lived presigned URL in the JSON response; the browser downloads directly from S3. This avoids ever base64-encoding a file through API Gateway and sidesteps the payload limit entirely as exports grow.

7.3 — Database connections from Lambda, inside the new dedicated VPC

Lambda can run many concurrent invocations, each potentially opening its own Postgres connection — the one thing that doesn't scale the same way a stateless container does. All seven domain Lambdas and the Aurora cluster sit in a new, dedicated VPC (10.20.0.0/16, two private subnets across two AZs — no custom VPC existed in the account to reuse, confirmed by an AWS CLI sweep). Since this app makes no outbound internet calls, there's no NAT Gateway: a free S3 gateway endpoint plus interface endpoints for Secrets Manager and CloudWatch Logs are all the networking this needs. The connection-count problem itself is deferred rather than solved on day one — Aurora Serverless v2 handles moderate concurrency reasonably at pilot scale, and an RDS Proxy in front of the cluster is the documented next step once traffic past pilot scale makes connection exhaustion a real risk, not before.

8. Phased plan

Phase 1

Scaffold both directories, nothing live yet

~2–3 days
  • sam init for backend/ (Python 3.12 runtime, "Hello World" template as a starting point only — every function gets replaced per §4); npm create vite@latest frontend -- --template react-ts for frontend/.
  • Copy design-system/css/*.css into frontend/src/styles/ and templates/partials/icons.html's sprite into the frontend's root HTML, unedited.
  • No changes anywhere in the existing repo root — it keeps deploying to Vercel exactly as it does today.
Phase 2

Backend: seven plain Lambda handlers, no framework

~1–2 weeks
  • Move database.py and allocation.py into a shared Lambda layer imported by every handler; move auth.py into AuthService, swapping the cookie for JWT issuance per §7.1.
  • Write each of the seven handlers in infra/resource-mapping/lba-backend-unified-resource-mapping-layer-oriented.json as a plain function — def lambda_handler(event, context): dispatching on path/method, parsing the API Gateway proxy event directly, returning a dict with statusCode/body. No request object, no dependency injection, no decorators.
  • Write the JWT authorizer Lambda and wire its REQUEST authorizer type into every protected route in template.yaml.
  • Define the Aurora Serverless v2 cluster in template.yaml with the scaling config from the registry (min 0.5 / max 8 ACU), including the new VPC, its two private subnets, and the three security groups (Lambda, Aurora, VPC endpoints) defined in the registry.
  • Test every route with sam local start-api against the existing dev Postgres (Aurora-compatible wire protocol, so local Postgres works fine for this) before touching AWS.
Phase 3

Frontend: build the component library, then the pages

~2–3 weeks
  • Build the 12 components in §5 first — everything else depends on them.
  • Build pages in order of how much they matter to an active LBA: dashboard → farmers → lots/new → lot result/export → farmer detail → settings/users → auth pages.
  • Each page is checked side-by-side against its current Jinja2-rendered counterpart (same screen, same data) before moving to the next.
Phase 4

Deploy both to AWS/staging, full parity pass

~1 week
  • sam deploy the backend to a staging AWS account/stage; deploy the frontend build to a staging URL (a Vercel preview deployment works fine for this).
  • Walk every route in §6 end to end on staging: signup → login → upload the real JIMGAF file → create a lot → accept/reject → export → farmer detail → settings.
Phase 5

Cut over

ongoing
  • Point the production domain at the new frontend build and the new API Gateway custom domain.
  • Keep the old Vercel + Neon deployment reachable (unlinked from the domain, not deleted) for a rollback window.
  • Only after that window passes cleanly: retire app.py, templates/, and the old Vercel project.

9. Effect on the existing app

  • Nothing about the live app changes until Phase 5. Every real LBA account (JIMGAF included) keeps working exactly as today, on the same Vercel + Neon deployment, for the full duration of Phases 1–4. The new work happens in two new directories that nothing in production imports or depends on.
  • Local dev changes from one process to two. Today it's one uvicorn process. Going forward it's sam local start-api for the backend and vite dev for the frontend, running side by side.
  • Deploys change from one command to two. vercel --prod for the whole app today becomes sam deploy (backend) + a frontend static deploy (Vercel can still do this — it's just serving a build folder, not running Python), kept independently versioned.
  • This supersedes the compute and database choices in the earlier AWS provisioning plan and cost estimate. Those documents assumed App Runner/Fargate compute and RDS-or-Neon. The confirmed direction is direct Lambda-to-API-Gateway integrations with no framework, Aurora PostgreSQL Serverless v2, and a new dedicated VPC provisioned for this project — both documents now carry a callout pointing here and to infra/resource-mapping/ for the current numbers (~$71/mo at pilot scale, down from ~$125/mo, mainly because Lambda's idle cost is near zero and no new NAT Gateway is needed).
  • No framework means no Mangum dependency and no cold-start-of-a-whole-app penalty. Each of the seven Lambdas only loads the code its own route needs, not the entire app — a smaller, more auditable blast radius per function than one Lambda running all 26 routes through a framework would have had.
